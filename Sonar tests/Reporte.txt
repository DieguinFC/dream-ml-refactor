# 1. `test_pipeline_config_model_params_complete`

### Nombre

```text
tests/apiTimeSeries_tests/test_patchtsmixer_full_pipeline.py::TestPipelineConfigSchema::test_pipeline_config_model_params_complete
```

Archivo:

`test_patchtsmixer_full_pipeline.py`

### Problema

El test espera que `model_params` contenga:

```python
"context_length"
```

Pero el pipeline genera un diccionario parecido a:

```python
{
    "channel_attention": False,
    "d_model": 16,
    "dropout": 0.2,
    "expansion_factor": 2,
    ...
}
```

sin incluir `context_length`.

El error exacto es:

```text
AssertionError: Missing model_params key: context_length
```

## Qué revisar

Buscar dónde se crea el diccionario `model_params`:

```bash
cd /workspaces/dream-ml-refactor

rg -n "model_params|context_length|pipeline_config" \
  DREAM-ML-backend/GEML/apiTimeSeries \
  DREAM-ML-backend/GEML/tests/apiTimeSeries_tests
```

Los archivos más importantes son:

- `train.py`
- `services.py`
- `test_patchtsmixer_full_pipeline.py`

## Solución recomendada

Agregar `context_length` al diccionario que se guarda en la configuración del modelo.

Por ejemplo:

```python
model_params = {
    "context_length": context_length,
    "prediction_length": prediction_length,
    "d_model": d_model,
    "num_layers": num_layers,
    "dropout": dropout,
    "expansion_factor": expansion_factor,
    "channel_attention": channel_attention,
}
```

El valor debe salir de la configuración real usada para entrenar el modelo. No conviene poner un valor fijo únicamente para satisfacer el test.

### Importante

Hay que distinguir entre:

- `context_length`: cantidad de pasos históricos utilizados como entrada.
- `prediction_length`: cantidad de pasos futuros predichos.

El valor debe ser el mismo que se utiliza para preparar los datos y configurar PatchTSMixer.

# 4. `test_active_mlflow_run_cleanup`

### Nombre

```text
TestTrainModelView::test_active_mlflow_run_cleanup
```

### Problema

El test espera:

```python
mlflow.end_run.assert_called_once()
```

pero `end_run()` no se llama.

La razón inmediata es que la vista termina antes con:

```text
No se encontró archivo CSV en la solicitud
```

Por lo tanto nunca entra en la parte que limpia el run activo.

## Solución recomendada

Primero corregir el orden de validación de la vista. Después garantizar que la limpieza de MLflow esté en un bloque `finally`.

Patrón recomendado:

```python
try:
    result = service.train_model_logic(csv_file, configuration_data)
    return JsonResponse(result, status=200)
except FileNotFoundError as exc:
    return JsonResponse(..., status=404)
except RuntimeError as exc:
    return JsonResponse(..., status=500)
except Exception as exc:
    logger.exception("Error inesperado durante el entrenamiento")
    return JsonResponse(..., status=500)
finally:
    if mlflow.active_run() is not None:
        mlflow.end_run()
```

Es importante que la limpieza ocurra tanto si:

- El servicio termina correctamente.
- Lanza `RuntimeError`.
- Lanza `FileNotFoundError`.
- Lanza una excepción inesperada.

## Validación

```bash
python -m pytest \
  tests/apiTimeSeries_tests/test_views_train_model.py \
  -k "active_mlflow_run_cleanup" \
  -q \
  --tb=short \
  --timeout=60
```

# 6. `test_training_service_runtime_error_returns_500`

### Problema

El test espera que un `RuntimeError` producido por el servicio llegue como:

```text
500
```

pero actualmente recibe:

```text
400
```

porque el servicio ni siquiera llega a ejecutarse: la vista falla antes al validar el CSV.

## Solución

Después de corregir las validaciones iniciales, comprobar que el manejo de excepciones tenga una rama específica:

```python
except RuntimeError as exc:
    logger.error("Error durante el entrenamiento: %s", exc, exc_info=True)
    return JsonResponse(
        {
            "status": "error",
            "message": "Error durante el entrenamiento",
            "error_details": str(exc),
        },
        status=500,
    )
```

No se debe convertir todo error en `400`. Un `400` indica una solicitud inválida del cliente; un `RuntimeError` del servicio normalmente es un error interno del servidor.
